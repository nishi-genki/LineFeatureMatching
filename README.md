# line_feature_matching

映像の各フレームから線特徴を検出し、隣接フレーム間で対応付けを行うツールです。

---

## 概要

本ツールは動画の連続フレーム間で線分（エッジ）を検出・マッチングし、その結果を動画・画像・CSVとして出力します。建物・道路・人工物など直線的な構造物を含むシーンでの映像解析、カメラ運動推定、シーン変化検出などへの応用を想定しています。

### 処理パイプライン

`config.json` の `stage` (1〜4) で処理の深さを切り替えられる。

```
入力動画
  │
  ▼
フレーム読み込み・歪み補正（camera.dist に基づく cv2.remap undistort）
  │
  ▼
線分検出（LSD または EDLines）＋近傍線分統合
  │
  ▼
LBD記述子の計算                                     [stage ≥ 2]
  │
  ▼
フレーム間LBDマッチング（Lowe's ratio test）
  │
  ▼
3D線分の画像平面への投影（projector.py）            [stage ≥ 3]
  │
  ▼
2D-3D対応の追跡・幾何マッチング・GOOPPnPL姿勢推定    [stage ≥ 4]
（tracking.py: LBD伝播 → 幾何対応 → 姿勢推定 → MAGSAC/RANSAC外れ値除去）
  │
  ▼
可視化フレームの生成・診断ログ記録（diagnostics.py）
  │
  ▼
出力動画 / PNG画像 / CSV / 診断ログ
```

| stage | 内容 |
|---|---|
| `1` | 線分検出のみ |
| `2` | ＋LBDフレーム間マッチング |
| `3` | ＋3D線分の画像平面への投影 |
| `4` | ＋2D-3D対応追跡・GOOPPnPL姿勢推定（既定） |

---

## 機能一覧

| 機能 | 内容 |
|---|---|
| 線分検出 | LSD（Line Segment Detector）または EDLines から選択可能 |
| 記述子計算 | LBD（Line Binary Descriptor）による特徴量記述 |
| マッチング | BinaryDescriptorMatcher + Lowe's ratio test |
| 向き正規化 | 線分の向きを「左→右」に統一してミスマッチを抑制 |
| 可視化 | 横並び2フレーム＋対応線の描画 |
| 出力 | 動画（mp4）、フレーム画像（PNG）、対応情報（CSV） |

## 依存環境

- Python 3.8 以上
- OpenCV（`opencv-contrib-python` が必要）

```bash
pip install opencv-contrib-python numpy
```

> **注意**: `opencv-python`（contrib なし）では `cv2.line_descriptor` および `cv2.ximgproc` が使えません。必ず `opencv-contrib-python` をインストールしてください。

## 検出器の選択

### LSD（デフォルト）

OpenCVの `LSDDetector` を使用します。精度が高く、長い線分を安定して検出できます。
**向いているシーン**: 建物・インフラ・人工構造物など直線が明確な映像

LSD固有のパラメータは `detection` および `descriptor` セクションで調整できます。

| パラメータ | キー | 目安 | 効果 |
|---|---|---|---|
| ピラミッドスケール | `lsd_octave_scale` | `1`〜`4` | 大きいほど粗い解像度で検出 |
| オクターブ数 | `lsd_num_octaves` | `1`〜`3` | 大きいほど多スケールで検出 |
| LSDスケール | `lsd_scale` | `0.5`〜`1.0` | 大きいほど細かい線まで検出 |

### EDLines

`cv2.ximgproc.createEdgeDrawing()` を使用します。LSDより高速ですが、短い線分が多く検出される傾向があります。
**向いているシーン**: リアルタイム処理が必要な場合、またはエッジが豊富なシーン

長い線分を優先したい場合は `edlines_min_length` を大きくしてください。

| パラメータ | キー | 目安 | 効果 |
|---|---|---|---|
| 最小線分長 | `edlines_min_length` | `30`〜`100` | 大きくすると短い線が除外される |

## 主要な内部処理

`stage` が上がるほど処理段数が増え、使われる内部処理も増える。以下は各処理の内容と、それを入れたことで何が改善するか（効果）をまとめたもの。

### 1. 線分の向き正規化（`detector.normalize_line_directions`） — すべての stage

LBD記述子は線分の向き（始点→終点）に依存するため、同じエッジでも検出ごとに始点・終点が逆になるとディスクリプタが変わりミスマッチが増える。全線分を「左→右（垂直なら上→下）」に統一することで、この向き依存によるミスマッチを構造的に防ぐ。垂直判定の許容誤差は `geometry.vertical_epsilon`。

### 2. 近傍線分の統合（`detector._merge_collinear_segments`、`detection.merge`） — すべての stage

歪み・遮蔽・検出器の癖により、本来1本のエッジが複数の短い断片として検出されることがある。角度差・垂線距離・直線方向の隙間がいずれも閾値以内の線分群をUnion-Findで連結成分にまとめ、最長メンバーの方向を基準に1本の線分へ統合する（長さ・本数フィルタの**前**に実施）。

**効果**: 断片化した短い線分は (a) LBD記述子が不安定になりやすく (b) `max_lines` の本数制限で切り捨てられやすい。統合によって太く長い線分になるため、フレーム間のLBDマッチングの本数・安定性が向上する。既定では無効（`enable: false`）。歪み補正の無効領域クリップ（後述）は統合の**前**に行う。統合後にクリップすると、捏造領域を挟んで無関係な断片を誤統合してしまうため。

### 3. 歪み補正と有効領域マスク（`pipeline.process_video`、`detector._clip_segments_to_mask`） — `projection.enable` かつ `stage` ≥ 3

歪み補正（`cv2.remap`、`camera.dist`）はフレーム単位で一度だけ行い、3D投影側は歪みなしの純粋なピンホール投影に統一している（投影側を歪ませる旧実装は廃止済み）。これにより歪み補正と投影の整合性を保っている。

`cv2.remap` の `BORDER_REPLICATE` は画角外の領域を周辺画素の引き伸ばしで滑らかに埋めるが、その内容は実シーンを反映していない。この「捏造領域」対策は2段構えになっている。

| 対策 | 対象 | 役割 |
|---|---|---|
| `BORDER_REPLICATE` | 画像全体 | 黒/実画像の境界という強いエッジそのものを無くす（境界自体が検出されるのを防ぐ） |
| 有効領域マスクによるクリップ（`valid_mask`） | 検出線分 | 繰り返し模様（ブラインド窓など）が引き伸ばされて実エッジの延長のように検出された場合に、無効領域にかかる区間を切り捨てる |

**効果**: どちらか一方だけでは不十分（実測で確認済み）。黒塗り＋クリップのみでは境界線自体が有効領域側の線として検出される問題を防げず、`BORDER_REPLICATE` のみでは引き伸ばされた模様が実エッジの延長として誤検出されたまま残る。2つを重ねることで両方のケースを塞いでいる。

### 4. 2D-3D対応の追跡とLBD伝播（`tracking.process_frame` Step「LBD伝播」） — `stage` ≥ 4

前フレームで3D線分と対応付けられた検出線分がLBDで現フレームの検出線分とマッチした場合、姿勢を介さずその2D-3D対応をそのまま引き継ぐ（追跡による引き継ぎは、幾何マッチングより優先される）。さらに `matching.propagation_filter.enable=true` の場合、引き継ぎの前に前後フレームの検出線分同士の**角度差・中点距離・長さ比**（姿勢に依存しない2D-2D比較、`matcher.is_match_consistent`）を確認し、満たさないLBDマッチは引き継ぎを行わない。

**効果**: LBDは特徴記述子ベースのマッチングであるため、大きな視線移動があってもフレーム間対応を追跡できる（元実装のオプティカルフローは移動量が小さい前提のため採用を見送った）。一方で記述子だけでは誤対応が紛れることがあり、`propagation_filter` は誤ったLBDマッチが2D-3D対応を汚染して以後何フレームも引き継がれ続ける事態を防ぐ。条件は中点間の**距離**なので、大きな視線移動時にも対応を棄却しすぎないよう `dist_th_px` は十分大きく取る必要がある（小移動前提で閾値を詰めるとLBD採用の利点を打ち消してしまう）。

### 5. 幾何学的対応付け（`line_matcher.LineMatcher2D3D`） — `stage` ≥ 3

LBDで引き継がれなかった検出線分について、現在の推定姿勢で3D線分を画像へ投影し、検出線分との幾何的な近さで対応付ける。2パス方式で、Pass 1（緩い角度差・垂線距離の閾値）で候補を集め、Pass 2（0.8倍に厳格化した閾値）でさらに絞り込み、最終的に投影線分とのオーバーラップ率が最大の候補を採用する（オーバーラップ率が `overlap_th` 未満なら不採用）。

**効果**: LBD伝播だけでは、追跡が途切れた線分（オクルージョン・検出失敗からの復帰など）に2D-3D対応を再付与できない。幾何マッチングがこれを補完し、`curr_2d3d` を毎フレーム一定数以上に保つ。

### 6. 紛らわしい3D線分ペアの入れ替え検出（`tracking._compute_confusable_pairs` / `process_frame`） — `projection.enable` かつ `stage` ≥ 3

世界座標上で数cm程度しか離れておらずほぼ平行な3D線分ペア（`dist_th=0.15`, `parallel_cos_th=0.99`）を事前に検出しておく。これらは検出ノイズに対して実差が小さすぎ、残差ベースの対応付けだけでは安定して区別できない。該当ペアについて、現在の推定姿勢で両方を投影したときの画面上の変位ベクトルと、実際に割り当てられている検出線分同士の変位ベクトルの向き（内積の符号）を比較し、逆向き（内積が負）なら対応が入れ替わっていると判断して2つの3D線分ラベルを交換する（対応自体は消さない）。

**効果**: 近接・平行な3D線分の対応が入れ替わったまま毎フレーム引き継がれる（LBD伝播のため）のを防ぎ、姿勢推定に渡す対応データの正しさを保つ。画面のX軸方向にずれたペアだけでなくZ方向（高さ）にずれたペアにも対応できるよう、画面X/Y成分両方で判定する。

### 7. 姿勢取得の優先順位（`tracking.acquire_pose`） — `stage` ≥ 3

1. `projection.rt_csv` に該当フレームの既知姿勢があれば最優先で使用
2. なければ `projection.marker_init_frames` の範囲内でのみマーカー/ArUco姿勢推定（`marker_pose.MarkerPoseEstimator`）
3. いずれも得られなければ前フレームの姿勢をそのまま引き継ぐ

**効果**: 既知姿勢がある区間ではそれを信頼のアンカーとして使い、未知区間ではマーカーで初期化したあと、GOOPPnPL追跡に委ねる構成。マーカーは常時検出し続けると（視野外に出た後の誤検出等で）むしろ姿勢が乱れるため、`marker_init_frames` で使用範囲を明示的に区切れるようにしている。

### 8. GOOPPnPLによる姿勢精密化と反転解対策（`line_pose._estimate_pose_core`） — `stage` ≥ 4

2D-3D線分対応から姿勢を求める最終ステップ。PnL（Perspective-n-Line）には原理的に鏡映対称な「反転解」が紛れ込む（GOOPPnPLが返す大域解の中に、正解と対称な別解が実数解・残差有限のまま含まれる）。本ツールでは次の選択規則で候補（J昇順）をフィルタし、最初に通った候補をOIPnPLで反復改良して最終姿勢とする。

```
is_real（実数解）
  & is_front（3D点群がカメラ前方にある）
  & r12 < 0（カメラY軸が下向き。y_down_constraint 有効時のみ、config で無効化可）
  & 再投影残差が有限
  → 上記を満たす J 最小の候補を採用
```

**調査結果（実データ test2, 577回の姿勢推定）**: 反転解は実際には2系統に分かれて現れることが分かった。

| 系統 | 特徴 | `is_front` フィルタで排除できるか |
|---|---|---|
| 上下反転系統 | カメラY軸が上を向く（`r12>0`）。水平軸まわり約180°回転 | できない（点群はカメラ前方に残る） |
| 平面鏡映系統 | カメラがマーカー平面の裏側に回り込む（カメラ中心のZ成分のみ反転） | できる（`is_front=False`） |

`is_front` 単体では上下反転系統を排除できないため、`y_down_constraint`（`r12<0`）を併用して両系統を排除している。この組み合わせにより、577回の推定で反転解の採用は**0件**（単純に「前フレーム姿勢に回転が近い方を選ぶ」方式では8件混入）。両フィルタをすり抜けた反転解は全データ中1件のみ発生したが、正解候補とJ値で2桁差があり、J最小選択で自動的に負けて無害だった。

前提として、ワールドZ軸が上向き・カメラY軸が常に下向きというリグ構成を仮定している（実データでは正解姿勢の `r12` は全800フレームで負、中央値-0.99）。構図が変わる（カメラを大きく傾ける等）場合は `line_matching.y_down_constraint: false` で無効化する。

フィルタを通る候補が1つも無かった場合は、GOOPPnPLが返す上位2候補から参照姿勢（前フレーム姿勢）に回転が近い方（参照が無ければ再投影残差が小さい方）を選ぶフォールバックに切り替える。

### 9. RANSAC/MAGSACによるロバスト推定（`line_pose._magsac_inliers` / `_ransac_inliers`） — `stage` ≥ 4、`line_matching.robust_method`

#### 残差の定義（`_line_residual`）

1対応あたりの残差は、**検出線分（2D）の両端点から、3D線分を現姿勢で投影した直線への垂線距離の平均**で定義する（点と直線の距離。投影線分の有限長は無視した「無限直線」として扱う）。

```
残差 = ( perp(検出線分の始点, 投影直線) + perp(検出線分の終点, 投影直線) ) / 2
```

投影前に、検出線分と投影線分の角度差が45°（`_ANGLE_PREFILTER_DEG`、固定値）を超える対応は無条件で残差 `inf` を返す。これは明らかに方向が異なる誤対応をロバスト推定の候補評価から早期に除外するための事前フィルタで、残差だけでは区別しづらい「近いが向きが違う」誤対応の誤採用を防ぐ。

#### 退化サンプルの除外（`_sample_is_degenerate`、`min_sample_angle_deg`）

RANSAC/MAGSACが毎反復で引く最小サンプル（`min_lines` 本）の3D線分方向が、全ペアで `min_sample_angle_deg` 未満しか離れていない（≒全部ほぼ平行）場合、そのサンプルからの姿勢候補生成をスキップする。

**調査でわかった効果**: ほぼ平行な線分だけで姿勢を解くと、その方向に沿った並進・回転成分が実質不定になる（開口問題）。このような偏った候補は、少数派だが実際には正しい「向きの異なる長い基準線」をたまたま外れ値側に弾き出しやすく、多数派の平行線だけを残してしまう退化が起きていた。候補生成の時点で退化サンプルを捨てることで、この種の誤ったインライア選択を防いでいる。

#### MAGSAC++ の重み・モデル選択・σ推定

ハード閾値でインライア/アウトライアを決めるRANSACに対し、MAGSAC（既定 `robust_method="magsac"`）はσ（ノイズスケール）が未知であることを前提に、σ ∈ `[0, sigma_max_px]` で積分消去した解析的なソフト重みを使う（`scipy` 不要）。

```
w(e) = erfc( e / (√2 · sigma_max_px) )      # e=0 で w=1、e→∞ で w→0
```

候補モデル選択は Σw(e) の最大化（ハード閾値で切った点数ではなく、残差の大きさに応じた重み付き合計）で行う。採用モデルが決まったあと、以下のLO（Local Optimization）ステップで仕上げる。

1. 最良モデルの残差が `sigma_max_px` 以下の対応だけで再フィット（最小サンプルでのフィットは残差がサンプル自身に過学習してほぼ0になり、σを過小評価するため）
2. スコアが改善する間（最大3回）繰り返す
3. 最終残差の**重み付き中央値**から σ を推定（`sigma_est = max(重み付き中央値 / 0.6745, 1.0)`）し、`3·sigma_est` 以内をインライアとする

**効果（ハード閾値RANSACとの比較）**: `sigma_max_px`（ノイズスケールの**上限**）はユーザが与えるが、実際のインライア判定閾値 `3·sigma_est` はその回の対応データから自動推定される。そのため、フレームごとに検出ノイズの大きさが変動しても、毎回同じ固定px閾値（`ransac_thresh_px`）を当てはめるRANSACより閾値のミスマッチが起きにくい。`robust_method: "none"` ではロバスト推定を行わずすべてを姿勢推定に使う。

#### 既知の限界：GOOPPnPL自体の非決定性

`io.use_fixed_seed: true` でPython側の乱数シードを固定しても、GOOPPnPL（姿勢精密化を行うC++ソルバ）の出力はフレームによって実行ごとにわずかに異なることが確認されている（残差が小数点以下の桁でぶれ、ごく僅かにRANSAC/MAGSACのインライア境界上にある対応の判定が反転する場合がある）。内部RNGまたは浮動小数点の縮約順序に起因すると見られ、Python側のシード固定では制御できない。再現性の検証（旧実装との挙動比較など）を行う際は、この非決定性をリファクタ等による差異と区別する必要がある（固定シードでの旧実装どうしの2回実行を比較する、という方法で区別できる）。

### 10. 姿勢ジャンプゲート（`tracking.process_frame` Step3） — `stage` ≥ 4、`line_matching.max_rot_jump_deg` / `max_trans_jump`

GOOPPnPLで精密化した姿勢が、前フレーム姿勢から見て物理的にあり得ない回転量・移動量のジャンプを起こしていた場合、その推定結果を棄却して前フレーム姿勢を維持する。`max_rot_jump_deg` ≤ 0 または `max_trans_jump` ≤ 0 の場合はそれぞれ無効。

**効果**: 反転解や対応の破綻（間違った3D線分の組を使った推定など）が紛れ込んだ場合、姿勢が一瞬だけ大きくジャンプしてすぐ戻る、という典型的な破綻パターンが出る。ジャンプゲートはこれを入口で止める最後の防衛線として働く。

### 11. Lowe's ratio test（`matcher.match_lines`） — すべての stage

kNN（k=2）で候補マッチを取得し、最近傍距離が2番目の近傍距離の `ratio_thresh` 倍未満のものだけを採用する。値を小さくすると厳しいマッチングになり偽対応が減るが、マッチ数も減る。

### 12. 診断ログ（`diagnostics.DiagnosticsLog`）

各処理の挙動を検証できるよう、処理ループとは別に以下のCSVを記録する（`<stem>_line_match_frames/` に出力）。

| ファイル | 内容 |
|---|---|
| `corr_diag.csv` | フレームごとの2D-3D対応1件ごと：対応元（`LBD`/`GEOM`）、対応する3D線分、再投影残差、RANSAC/MAGSACでの外れ値判定 |
| `track_diag.csv` | フレームごとの検出数・LBDマッチ数・追跡/幾何由来の2D-3D対応数 |
| `stability_diag.csv` | フレーム間のカメラ移動量・回転量（姿勢の安定性の目視検証用） |
| `magsac_diag.csv` | MAGSAC呼び出しごとのσ推定内訳（残差分布・重み付き中央値・推定σ・インライア数など） |
| `pose_diag.csv` | GOOPPnPLの姿勢推定1回ごとの全候補解（J・実数解判定・前方判定・残差・採用フラグ等） |

これらは上記8・9項の調査（反転解の分類、残差・σ推定の検証）に実際に使ったログであり、パラメータ調整やリグレッション確認の際にまず当たるべき出力。

## パフォーマンスのヒント

高解像度映像（1080p以上）では処理が重くなりがちです。以下の対処が有効です。

- `resize_width: 960` などでリサイズして処理する
- `max_lines: 100` で検出数を抑える
- `detector: "edlines"` に切り替える（LSDより高速）
- フレームレートの高い動画は事前に間引きしておく

## 注意事項

- `cv2.line_descriptor` および `cv2.ximgproc` はOpenCVのcontribモジュールに含まれます。`opencv-contrib-python` が必須です。
- EDLinesのPythonバインディングでは `EdgeDrawing_Params` による詳細なパラメータ設定ができない場合があります（バージョン依存）。
- 出力動画は `mp4v` コーデックを使用します。環境によっては再生できない場合があるため、その場合はffmpegでH.264に変換してください。

```bash
ffmpeg -i output/<stem>_line_match.mp4 -vcodec libx264 output/<stem>_line_match_h264.mp4
```
